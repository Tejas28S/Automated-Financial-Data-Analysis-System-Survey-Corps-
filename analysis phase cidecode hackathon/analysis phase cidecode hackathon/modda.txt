PART 2 — CODEBASE SUMMARY (ALL FILES IN THE ANALYSIS PHASE)
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

ROOT FILES
──────────
  analysis_engine/cli.py
    • Command-line entry point.
    • Arguments: --input (CSV or folder), --output-dir, --trace-credits,
      --no-llm, --verbose.
    • Calls AnalysisPipeline.run(), then print_summary(), then write_rich_report().
    • Auto-detects project root by walking up directory tree to find
      analysis_engine/ folder.
    • Writes report to analysis_op/<case_name>/report.json.

  analysis_engine/pipeline.py
    • Master orchestrator. Runs all steps in prescribed order:
        Step 1: load_inputs() → normalizes CSV into internal format
        Step 2: initialize_database() + load_transactions() → SQLite
        Step 3: compute_baseline() → statistical thresholds
        Step 3b: validate_balances() → balance gatekeeper (Pattern 3)
        Step 3c: finalize_counterparty_statistics() → update thresholds
        Step 4: resolve_counterparties() → NEFT/IMPS/UPI/LLM parsing
        Step 5a: detect_duplicate_cross_check() → Pattern 1
                 detect_reversals() → Pattern 2
                 detect_structuring() → Pattern 7
                 detect_requested_money_trails() → Pattern 10
        Step 5b: build_money_flow_graph() → Pattern 8
        Step 5c: detect_round_trips() → Pattern 4
                 detect_transit_accounts() → Pattern 5
                 detect_accumulation_accounts() → Pattern 6
                 detect_circular_flows() → Pattern 9
        Step 6: score_accounts() → ranked suspicious account list
        Step 7: assemble AnalysisResult → persist to SQLite + JSON

  analysis_engine/ingest.py
    • Adaptive CSV parser.
    • Column detection: date, debit, credit, account_id, txn_id, narration.
    • Handles multiple date formats (DD/MM/YYYY, MM-DD-YYYY, etc.).
    • Mixed debit/credit formats, missing fields, renamed columns.
    • Adds source_bucket (clean/flagged/duplicate), eligible_for_detection,
      confidence_tier, exclusion_reason columns.
    • Applies Critical Design Rule: balance_mismatch rows → excluded.

  analysis_engine/database.py
    • Creates and manages SQLite database (analysis.db per run).
    • Tables: transactions, accounts, documents, baseline_summary,
      counterparty_cache, balance_validation, possible_same_owner.
    • Indexes on account_id, date, eligible_for_detection for fast queries.
    • All later steps read from SQLite only — never from CSVs again.

  analysis_engine/baseline.py
    • Computes statistical thresholds from the loaded dataset at runtime.
    • Outputs: median/P95/P99 amounts, date range, account counts,
      per-account credit/debit totals, throughput ratios.
    • Derives ALL pattern thresholds dynamically:
        - reversal_window_days (from typical transaction gap)
        - round_trip_window_days (baseline settlement time × multiplier)
        - transit_throughput_ratio_min (from high_ratio_quantile)
        - transit_volume_min (from high_volume_quantile)
        - accumulation_credit_min (P75 of total credits per account)
        - structuring_individual_amount_max (P99 of amounts)
        - structuring_collective_amount_min (high_value_amount × cluster)
    • NEVER hardcodes numbers based on a specific dataset.

  analysis_engine/balance.py
    • Walks each account's transactions chronologically.
    • Checks: previous_balance + credit - debit ≈ current_balance (±1.0).
    • Rows causing mismatch → marked excluded, pattern-3 finding raised.
    • Acts as the gatekeeper: even "clean" rows can fail if ordering is wrong.

  analysis_engine/counterparties.py
    • Resolves the "other party" in each transaction from narration text.
    • Step 1 — Deterministic: regex for NEFT/IMPS/RTGS/UPI/ATM/POS/CHQ/CLG/
      ECS/NACH. Extracts IFSC codes (4 letters + 0 + 6 alphanumeric),
      account-like numeric sequences, UPI VPA handles (name@bank).
    • Step 2 — LLM fallback (Groq llama-3.1-8b-instant): only for non-empty,
      non-generic narrations that deterministic parsing couldn't resolve.
    • Caches LLM results by normalized narration in SQLite counterparty_cache.
    • Writes: counterparty_account, counterparty_ifsc, counterparty_name_raw,
      counterparty_resolution_method columns.
    • Cross-references accounts sharing same normalized holder name →
      stored in possible_same_owner table (never auto-merged).

  analysis_engine/graph.py
    • Builds a directed weighted MultiDiGraph (NetworkX).
    • Nodes = account IDs. Edges = transactions with amount/date/txn_id attrs.
    • Mirrored debit+credit pairs for same transfer → single edge.
    • Reusable by all graph-based detectors (Patterns 4, 5, 6, 9).

  analysis_engine/models.py
    • Finding dataclass: finding_id (SHA-256 hash), pattern_id, pattern_name,
      accounts, txn_ids, explanation, confidence_tier, details dict.
    • AnalysisResult: all findings, suspicious_accounts, baseline_summary,
      counterparty_resolution, excluded_rows, graph, run_metadata.
    • PATTERN_CATALOG: mapping of pattern IDs 1–10 to names/keys.

  analysis_engine/config.py
    • Frozen AnalysisConfig dataclass with universal limits:
        balance_tolerance=1.0, money_epsilon=0.01
        duplicate_date_window_days=1, duplicate_amount_relative_tolerance=0.005
        duplicate_narration_similarity=0.80
        reversal_amount_relative_tolerance=0.02
        default_round_trip_window_days=30, max_cycle_length=6
        upper_amount_quantile=0.99, high_volume_quantile=0.75
        enable_llm_fallback=True
    • These are NEVER dataset-specific tuning values.

  analysis_engine/scoring.py
    • Ranks accounts by count of DISTINCT pattern types that flagged them.
    • Primary score = distinct pattern count. Secondary = total finding count.
    • Pattern breakdown stored: how many findings per pattern per account.
    • Five structuring flags ≠ one round-trip + one accumulation (by design).

  analysis_engine/output.py
    • Console printer for pipeline results.
    • Fixed UnicodeEncodeError on Windows by replacing Unicode arrows.
    • Prints full finding breakdown with _print_finding_details().

  analysis_engine/rich_report.py
    • Generates analysis_op/<case_name>/report.json after every run.
    • Enriches each Finding with: primary_amount, date_context, duration_days,
      flow_path, flow_path_readable, pattern-specific blocks (round_trip {},
      transit {}, accumulation {}, structuring {}, duplicate {}, reversal {},
      circular_flow {}, money_trail {}), source_documents, raw_details.
    • Assembles full report: report_metadata, detection_summary,
      dataset_summary, counterparty_resolution, exclusion_summary,
      graph_summary, suspicious_account_rankings, findings_by_pattern,
      all_findings (flat list).
    • Finding IDs are SHA-256 hashes — deterministic, deduplication-safe.

  analysis_engine/utils.py
    • Shared utility functions used across the engine.

DETECTORS (analysis_engine/detectors/)
──────────────────────────────────────
  Pattern 1 — duplicate.py
    • Groups rows by same account + similar amount (±0.5%) within 1-day window.
    • Checks narration similarity ≥ 80% (SequenceMatcher).
    • Reconciles with extraction-flagged duplicates: reports missed + false +ve.
    • Never relies on is_reversed/duplicate_of columns as detection logic.

  Pattern 2 — reversal.py
    • Finds debit→credit pairs of same/near amount within baseline window.
    • Uses reference number and narration evidence to confirm reversal.
    • Never flags intentional credit-backs as reversals using hard rules.

  Pattern 3 — balance.py (balance.py in root)
    • Per-account running balance walk.
    • Flags only unexplained chain failures as findings.
    • Account-level validation metrics always available even when no finding.

  Pattern 4 — round_trip.py
    • DFS on the money-flow graph to find cycles where money returns to origin.
    • Window = baseline-derived round_trip_window_days (default max 30).
    • Checks edge amounts: each hop must retain ≥ 60% of previous amount.
    • Reports path, duration_days, edge_amounts.

  Pattern 5 — transit.py
    • Flags accounts where total_debit ≈ total_credit (throughput ratio high).
    • Threshold: throughput_ratio ≥ transit_throughput_ratio_min AND
      total_volume ≥ transit_volume_min AND txn_count ≥ min_txn_count.
    • All thresholds are baseline-derived.

  Pattern 6 — accumulation.py
    • Flags accounts with high total_credit from many counterparties
      but very low outflow (outflow/inflow ratio below threshold).
    • Threshold: credit_min from P75 of all account credits.

  Pattern 7 — structuring.py
    • Groups by account + date window.
    • Flags groups where individual amounts < individual_amount_max
      BUT daily aggregate > collective_amount_min AND count ≥ min_count.
    • Classic smurfing: many small → one large.

  Pattern 8 — graph_builder.py
    • Constructs the reusable MultiDiGraph from all eligible transactions.
    • This is infrastructure, not a detector itself.

  Pattern 9 — circular.py
    • Multi-hop cycle detection (up to 6 hops: A→B→C→D→A etc.).
    • Uses NetworkX simple_cycles on observed accounts (bounded graph).
    • Each cycle edge validated: must have real transaction support.
    • Avoids A→B→A (that is Pattern 4); needs length ≥ 3.

  Pattern 10 — money_trail.py
    • Trace API: trace_credit(txn_id) → follows credited amount through
      subsequent debits (FIFO allocation).
    • Stops when traced amount exhausted or account pre-credit balance reached.
    • Only runs for explicitly requested credit txn IDs (--trace-credits flag).

  detectors/common.py
    • Shared detection utilities: narration similarity, amount tolerance checks.

REPORT.JSON STRUCTURE (per case):
  Every analysis_op/<case>/report.json contains:
  • report_metadata      → case name, input file, generation timestamp, runtime
  • detection_summary    → total findings, flagged accounts, patterns triggered,
                           top suspect account + score
  • dataset_summary      → total/eligible/excluded rows, accounts, date range,
                           median/P95/P99 amounts, ALL runtime thresholds
  • counterparty_resolution → eligible rows, resolved rows, resolution rate %,
                              method breakdown, LLM call count, ledger pairs
  • exclusion_summary    → balance_mismatch count, duplicate count, total excluded
  • graph_summary        → node count, edge count
  • suspicious_account_rankings → ranked list with distinct pattern scores,
                                   finding counts, pattern breakdowns, finding IDs
  • findings_by_pattern  → all 10 patterns, even if 0 findings (never omitted)
  • all_findings         → flat list of every finding, each with:
      - finding_id (20-char SHA-256 hex), sequence, pattern ID/name/key
      - confidence_tier (high/medium/low)
      - explanation (plain English, non-technical)
      - accounts list, transaction_ids list
      - primary_amount, date_context, duration_days
      - flow_path + flow_path_readable (for cycles)
      - pattern-specific blocks (round_trip{}, transit{}, structuring{} etc.)
      - source_documents, raw_details

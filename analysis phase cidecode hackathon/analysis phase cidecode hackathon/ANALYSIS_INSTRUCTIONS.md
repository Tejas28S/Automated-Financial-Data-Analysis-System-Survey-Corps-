## What You Are Given (Input Contract)

The extraction phase produces exactly three CSV files per case/session:

`txn_id, doc_id, account_id, date, narration, reference, debit_amount,

You will receive these three files for the real case data, and separately,

## Critical Design Rule — Read Before Touching Anything Else

**Balance-mismatched rows are not "uncertain data," they are wrong data.**

A row flagged with `flag_reason = balance_mismatch` means extraction produced
a number that does not reconcile against the bank's own running balance. Since
the bank's own statement is internally consistent by construction (their
computer generated both the transactions and the balance from the same ledger),
any mismatch is proof of an extraction defect, not a real-world anomaly. You do
not know *which* field is wrong (amount misread, row skipped, debit/credit
swapped) — only that something is.

**Rule: pattern detectors only ever run on rows that reconcile.**

- `clean_transactions.csv` rows → eligible for detection, full confidence
- `flagged_transactions.csv` rows where `flag_reason != balance_mismatch`
  (e.g. a row with a low-confidence narration but a balance that checks out)
  → eligible for detection, but every finding touching this row must be
  labeled `lower_confidence` with the specific flag reason attached
- `flagged_transactions.csv` rows where `flag_reason == balance_mismatch`
  → EXCLUDED from all pattern detection. Never feed these into any detector.
  They go into a separate output: "Excluded from analysis — extraction error,
  needs manual review," listed with their source document and page if
  available.
- `duplicate_transactions.csv` rows → EXCLUDED from pattern detection by
  default (to avoid double-counting the same real money movement as two
  events). List them separately as "Suspected duplicates — review before
  treating as independent events." Do not silently merge or delete them.

This rule is not optional and must not be "improved" or reinterpreted during
implementation. If you believe an exception is warranted, stop and ask rather
than deciding unilaterally.

## The 10 Patterns to Detect (Locked List — Build Exactly These, No Others)

Do not add patterns beyond this list. Do not skip any of them. If you believe
a pattern cannot be reliably detected with the given data, say so explicitly
in your output rather than silently omitting it.

1. **Duplicate detection cross-check** — independent of the extraction-provided
   `duplicate_transactions.csv`, re-verify using same account + same amount +
   same/adjacent date + similar narration. Reconcile with what extraction
   already flagged; report any the extraction missed or any false positives
   extraction raised.

2. **Failed/reversed transaction detection** — a debit followed by a credit of
   the same (or near-same) amount on the same or adjacent account within a
   short window, indicating a reversal rather than two real movements.

3. **Balance consistency validation** — for every account, confirm
   `previous_balance + credit - debit ≈ current_balance` within a small
   tolerance, walking chronologically. (Note: this is also your gatekeeper
   check feeding the exclusion rule above — run it on the merged eligible set
   too, since even "clean" rows can have ordering issues across multiple
   source documents for the same account.)

4. **Round-trip detection** — money leaves an account and returns to the same
   account, directly or via one or more intermediary accounts, within a
   reasonable time window (default 30 days, but compute this relative to the
   dataset's own typical settlement times rather than hardcoding blindly).

5. **Transit / pass-through account detection** — an account where money in
   ≈ money out (high throughput ratio) over a meaningful transaction volume,
   indicating the account is a conduit rather than a destination.

6. **Accumulation account detection** — an account receiving from many distinct
   counterparties while sending out very little, indicating a collection point.

7. **Structuring / smurfing detection** — multiple transactions from the same
   account, same day (or short window), each individually below a threshold,
   collectively representing a significant sum — threshold computed relative
   to this dataset's own distribution, not a fixed number.

8. **Money flow graph construction** — build the directed account-to-account
   network from counterparty-resolved transactions. This is not a detector
   itself; it is the structure that patterns 4–7 and 9 query.

9. **Circular flow / multi-hop cycle detection** — generalization of pattern 4
   to cycles of length 3 or more (A→B→C→A), found via cycle detection over the
   graph from pattern 8.

10. **Money trail tracing** — given a specific credit into an account, trace
    forward (FIFO: oldest debits first) to show which subsequent outgoing
    transactions plausibly consumed that incoming money, until the traced
    amount is exhausted or the account's pre-credit balance is reached.

## Required Counterparty Extraction Step (Comes Before Patterns 4, 5, 6, 8, 9)

Patterns 4, 5, 6, 8, and 9 require knowing which account is connected to which
other account. This information lives inside the free-text `narration` field
and is not a separate column.

Build a counterparty-resolution step that:

- Uses deterministic parsing first: recognize standard Indian transaction
  vocabulary (NEFT, IMPS, RTGS, UPI, ATM, POS, CHQ, CLG, ECS, NACH) and extract
  IFSC codes (pattern: 4 letters, then `0`, then 6 alphanumeric), account-like
  numeric sequences, and UPI VPA handles (`name@bank`) using regex.
- Falls back to an LLM call ONLY when deterministic parsing finds nothing
  AND the narration is non-empty AND non-generic (skip LLM calls on narrations
  that are clearly internal, e.g. "Opening Balance", "Interest Credit").
- Caches LLM results by normalized narration pattern so the same phrasing is
  never sent to the LLM twice.
- Where a counterparty cannot be resolved at all, leave it null. Do not guess.
  A transaction with no resolved counterparty still participates fully in
  single-account patterns (1, 2, 3, 7, 10) — it simply does not contribute an
  edge to the graph used by patterns 4, 5, 6, 8, 9.
- Additionally extract and store the counterparty's name (from narration) where
  present, separate from the counterparty account number. Two different account
  numbers with the same extracted holder name should be cross-referenced and
  surfaced as "possibly same owner" — do not auto-merge them, just flag the
  possibility for the investigator.

This step writes its output as new columns on the working table:
`counterparty_account`, `counterparty_ifsc`, `counterparty_name_raw`,
`counterparty_resolution_method` (deterministic / llm / unresolved).

## Required Baseline Statistics Step (Comes Before All Pattern Detectors)

Before any pattern detector runs, compute baseline statistics from whatever
data is actually loaded for that run — never from a hardcoded number derived
from any specific dataset you've seen during development. This includes,
at minimum: median and percentile transaction amounts, median transactions
per account, date range, per-account total credit/debit/throughput ratio,
and per-account unique-counterparty counts.

Every threshold used anywhere in patterns 4–7 must be computed from this
baseline at runtime, not hardcoded as a literal number in the detector code.
If a detector contains a bare numeric literal that isn't a universal constant
(e.g. days-in-a-month, or a literal that came from regulatory definition like
a specific CTR threshold which should be configurable, not hidden), that is
a defect — fix it before moving on.

Output this baseline as a human-readable dataset summary (counts, ranges, top
accounts by volume/connectivity) — this is shown to the investigator before
any pattern results, regardless of whether any pattern fires.

## Architecture / Data Flow (Build in This Order)

```
clean_transactions.csv ─┐
flagged_transactions.csv├─→ [1. Merge + Label] ─→ [2. SQLite load] ─→
duplicate_transactions.csv┘

[2. SQLite load] ─→ [3. Baseline stats] ─→ [4. Counterparty resolution] ─→

[4] ─→ [5a. Single-account detectors: patterns 1,2,3,7,10]
[4] ─→ [5b. Graph construction: pattern 8] ─→ [5c. Graph detectors: 4,5,6,9]

[5a + 5c] ─→ [6. Suspicion scoring / signal combination] ─→
[6] ─→ [7. Structured findings output] (this is the END of analysis phase —
        report/PDF/Streamlit rendering is a separate later phase, out of scope here)
```

**Step 1 — Merge + Label:** Load all three CSVs. Add a `source_bucket` column
(`clean` / `flagged` / `duplicate`). Apply the exclusion rule from the Critical
Design Rule section: rows with `flag_reason == balance_mismatch` get
`eligible_for_detection = False`; duplicate-bucket rows get
`eligible_for_detection = False` by default; everything else gets
`eligible_for_detection = True` with a `confidence_tier` of `high` (clean) or
`low` (flagged-but-not-balance-mismatch).

**Step 2 — SQLite load:** Convert the merged table into a SQLite database file
(not in-memory only — persist to disk so re-runs don't require re-merging).
Three tables: `transactions` (every row, with `source_bucket`,
`eligible_for_detection`, `confidence_tier` columns added), `accounts`
(one row per unique account_id with aggregated stats — populate AFTER step 3),
`documents` (one row per doc_id). Index `transactions` on `account_id`, `date`,
`eligible_for_detection`. This is the only place CSV-to-SQLite conversion
happens; every later step reads from this database, never from the CSVs again.

**Step 3 — Baseline stats:** As specified above. Write results both back into
the `accounts` table and as a separate retrievable summary object/table
(`baseline_summary`).

**Step 4 — Counterparty resolution:** As specified above. Runs only on rows
where `eligible_for_detection = True`.

**Step 5a — Single-account detectors (patterns 1, 2, 3, 7, 10):** Each is an
independent function taking the SQLite connection + baseline as input,
returning a structured list of findings. Each finding must include: the
pattern name, the account(s) involved, the specific `txn_id`s that triggered
it, a plain-English explanation, and a `confidence_tier` (inherited from the
lowest confidence_tier among its contributing transactions).

**Step 5b — Graph construction (pattern 8):** Build a directed graph from
`counterparty_account` links among `eligible_for_detection = True` rows only.
Nodes = accounts. Edges = transactions, carrying amount/date/txn_id as edge
attributes. This graph object must be reusable by 5c without rebuilding.

**Step 5c — Graph detectors (patterns 4, 5, 6, 9):** Each operates on the graph
from 5b plus the SQLite data for amount/ratio checks. Same finding structure
as 5a.

**Step 6 — Suspicion scoring:** For each account, count distinct pattern types
that flagged it (not just count of flags — five structuring flags on one day
should not outweigh one round-trip + one accumulation flag). Produce a ranked
list. Every score must show its breakdown (which patterns fired, how many
times each) — no opaque single number without the underlying components shown
alongside it.

**Step 7 — Structured findings output:** Consolidate everything into one
output structure: dataset baseline summary, ranked suspicious accounts with
score breakdowns, full finding list per pattern (all 10, even if some have
zero findings — report zero findings explicitly, don't omit the pattern),
the excluded-rows list (balance mismatches + duplicates) for manual review,
and the graph object for downstream visualization. This is the final
deliverable of the analysis phase.

## Testing Protocol (Mandatory, Follow Exactly)

You will be given synthetic test data: **3 CSV-triplets per pattern** (each
triplet = its own clean/flagged/duplicate set), i.e. 3 independent synthetic
test cases per pattern, 30 test cases total across the 10 patterns.

**Use exactly 2 of the 3 test cases per pattern to build and tune each
detector. The 3rd test case per pattern is held out and must NOT be looked at,
read, or used in any way while writing or adjusting that detector's code.**

After a detector is implemented and passes on its 2 build cases, run it ONCE
against the held-out 3rd case. Report the result as-is. Do not iterate against
the held-out case — if it fails, that is signal to revisit the detector's
*general logic* (not to special-case the held-out file), and you must rebuild
using only the original 2 build cases again, then re-test against the held-out
case only once more. Do not loop this more than twice per pattern. If it still
fails on the second attempt, report it as a known limitation rather than
continuing to iterate against held-out data — iterating against the supposedly
unseen case defeats its entire purpose.

**Do not run any detector against the full 162-file real dataset during
development.** Validate entirely on the synthetic triplets first. Only after
all 10 detectors pass their build cases and have been checked once against
their held-out case should the full pipeline be run once against real case
data, as a final integration check, not as a debugging tool.

**Before writing any detector for a given pattern, read both build-case CSVs
manually (print them, inspect them) and state in writing what you expect each
detector to find — which accounts, which transactions — before running any
code.** This is the known-answer check: you must know the right answer before
the code tells you, the same discipline as the round-trip example already
validated earlier in this project. If your detector's actual output does not
match your stated expectation, that is a bug, not a dataset quirk.

## Anti-Overfitting Rules (Non-Negotiable)

Reject any implementation that violates these. Self-check before declaring any
detector done:

- No bank name, account number, account holder name, or specific narration
  string appears anywhere in detector logic, as a literal, a comparison
  target, or a special case.
- No numeric threshold is a bare literal unless it is computed from the
  baseline at runtime or is a universal constant. If you typed a number
  because it "looked right" on a specific test file, remove it and replace it
  with a baseline-derived value.
- Every fix or detector must be explainable in one sentence using only general
  banking/graph vocabulary, with no reference to any specific file, bank, or
  test case. If you cannot write that sentence, the logic is too specific.
- After finishing each detector, explicitly state: "this detector was not
  tuned using the held-out case for pattern N" — confirm this in writing for
  every pattern.
- If fixing a detector to pass one build case breaks its result on the other
  build case for the same pattern, that is a regression — do not proceed until
  both build cases pass simultaneously with the same code.
